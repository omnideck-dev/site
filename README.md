# omnideck Site — Content Guide

This is the public site for omnideck. Content is written in Markdown with TOML front matter. No build tools or Node.js required.

## First-time setup

Clone the repo. No npm install, no build step, no additional setup required.

---

## Previewing the site

```bash
./arbor preview
```

Opens a live-reloading dev server at `http://localhost:8080`. Changes to content, templates, and CSS are picked up automatically.

---

## Production build

Run the production build in a container so its generated data and output stay
outside the checkout:

```bash
docker build --platform linux/amd64 --file container/Dockerfile .
```

## Content types

### Blog posts

**Location:** `content/blog/<slug>.md`

```toml
+++
title    = "Your Post Title"
date     = 2026-01-15
draft    = false
tags     = ["tag-one", "tag-two"]
template = "templates/types/blog.html"

[extra]
description    = "One or two sentences shown in previews and meta tags."
author         = "Your Name"
featured_image = "/images/your-image.jpg"
+++

Your content here...
```

| Field | Required | Notes |
|---|---|---|
| `title` | yes | Displayed as the page `<h1>` |
| `date` | yes | Format: `YYYY-MM-DD` |
| `draft` | yes | Set `true` to hide from the live site |
| `tags` | no | Array of lowercase-kebab strings — see [Tags](#tags) below |
| `template` | yes | Always `"templates/types/blog.html"` for blog posts |
| `description` | no | Used in meta tags and the blog listing |
| `author` | no | Shown below the title |
| `featured_image` | no | Path under `static/images/` — e.g. `/images/my-photo.jpg`. Shown full-width above the title and used for social link previews. |

To create a new post stub:

```bash
./arbor new blog my-post-slug
```

## Tags

Tags appear as chips on blog posts and in the blog sidebar. Use lowercase-kebab format in frontmatter:

```toml
tags = ["open-source", "local-ai", "new-tag"]
```

**Tags are managed automatically.** On every deploy, CI runs `bash scripts/sync-data.sh`, which:
- Updates `data/tags.toml` with current tag counts
- Creates any missing `content/blog/tags/<slug>.md` listing pages

You never need to touch `data/tags.toml` or the tag pages directly.

To run manually:

```bash
bash scripts/sync-data.sh
```

## Site data files

These files are generated by `scripts/sync-data.sh` and should not be edited by hand:

| File | What it does |
|---|---|
| `data/tags.toml` | Tag names, slugs, and post counts — drives the blog sidebar and tag listing pages |
| `data/homepage.toml` | Latest blog post title, date, and URL — drives the homepage’s “From the blog” section |
| `data/desktop_release.toml` | Latest published desktop installer release and its packages/checksums |
| `data/releases.toml` | Latest published ships and the 30-entry “What’s new” feed |
| `static/releases.json` | Deterministic release snapshot used to detect changes and verify deployed pages |

Synchronization reads all pages of releases from `omnideck-dev/omnideck` and
`omnideck-dev/cli`. Drafts and unpublished releases are excluded; previews are
included and labeled. Dates reflect GitHub publication timestamps in UTC.
The homepage shows the latest ship across app/runtime (`app-v*`), desktop
installer (`v*` in the app repository), and CLI (`v*` in the CLI repository)
streams. Short excerpts come from the published notes, with links to the full
notes. A separate CLI/runtime release does not replace a desktop bundle.

Downloads select the newest published desktop tag, independently of runtime
ships. All ten advertised installer packages and their SHA-256 checksum assets
must exist. A partially published desktop release or GitHub API failure fails
the build instead of silently reverting to an older release.

### Automatic release updates

The deploy workflow checks for new or edited release records every 30 minutes
and rebuilds/redeploys when the published snapshot differs. GitHub may delay
scheduled runs, so this is an expected cadence rather than a delivery SLA.
Unchanged scheduled runs leave the published site alone. Pushes to site `main`
and manual runs always deploy; pull requests build and verify without publishing.
The workflow also accepts a `release-published` repository-dispatch event for an
optional immediate trigger from release tooling. Polling works without adding
cross-repository secrets or changing either source repository’s release workflow.

Every deployment waits for GitHub Pages propagation and verifies the homepage,
release feed, installer version, package URLs, checksum URLs, and release-note
links against the snapshot it built. An additional daily run at 13:23 UTC checks
the live site and links even when nothing shipped. Failures mark the Actions run
failed and add a job summary; maintainers should enable GitHub Actions failure
notifications for this repository. Existing published pages remain available
if a new build fails.

To run focused regression tests:

```bash
python3 -m unittest discover -s tests -v
```

The production container runs these tests, syncs release data, runs Arbor checks,
builds the site, and verifies the built pages. To verify an extracted build or
deployed site against its build snapshot:

```bash
python3 scripts/verify-site.py public --expected public/releases.json
python3 scripts/verify-site.py https://www.omnideck.dev \
  --expected public/releases.json --check-downloads
```

The second command compares the live site with that saved snapshot. The workflow
always generates a fresh snapshot from GitHub before making this comparison.

## Images

Place images in `static/images/` and reference them as `/images/filename.jpg`.

For blog post hero images, set `featured_image` in the front matter. The image appears full-width above the post title and is included in Open Graph meta tags for social previews.

---

## Drafts

Set `draft = true` in any file's front matter to exclude it from the live site. Drafts are visible during local preview by default.
